# AI Todo Coach API 구조 논의

## 회의 목적
AI 기능 도입에 따른 서버 및 클라이언트 통신 구조 설계, 보안 강화 방안 확립, 그리고 향후 RAG 연동을 위한 API 인터페이스 표준을 수립하기 위함이다.

## 참석자
개발자, AI 어시스턴트, 프로젝트 담당자

## 논의 내용

### API 호출 구조
보안 및 자원 관리 측면에서 브라우저 클라이언트가 OpenAI API를 직접 호출하는 방식은 원천 배제하기로 합의하였다. 모든 AI 요청은 자체 Node.js 및 Express 서버를 경유해야 하며, 민감 정보인 API key는 서버 환경 변수에서만 철저히 관리한다. 서버는 클라이언트의 대화 요청을 받아 OpenAI Responses API와 통신하고 그 결과를 정제하여 클라이언트에 전달하는 중계 및 통제 역할을 전담한다.

### Todo 처리
현재 운영 중인 Todo 데이터는 사용자 환경의 연속성과 가벼운 실행 구조를 유지하기 위해 기존 브라우저 localStorage에 유지하기로 결정하였다. AI가 자연어 대화 도중 사용자의 할 일을 조회하거나 수정할 때는 사전에 정의된 Todo Tool Calling 체계를 필수적으로 거치도록 한다. 허용된 도구는 create_task, update_task, complete_task, delete_task, list_tasks의 다섯 가지로 한정한다. 특히 데이터 유실 위험이 큰 delete_task 작업의 경우 AI의 판단만으로 즉각 삭제하지 않고, 클라이언트 UI 차원에서 사용자에게 명시적인 확인 팝업을 띄워 승인을 얻은 후 실행하도록 강제한다.

### RAG 도입
차기 마일스톤인 RAG 구축 단계에서는 외부 문서 검색 결과와 기존 Todo Tool Calling이 하나의 대화 세션 안에서 유기적으로 결합되어야 한다는 점에 의견을 모았다. AI는 문서를 검색해 근거를 확보한 뒤, 필요 시 할 일 등록이나 갱신 도구를 연쇄적으로 호출할 수 있어야 한다. 이때 검색된 문서 내용은 시스템에 대한 무조건적인 실행 지시가 아니라 어디까지나 답변 생성을 위한 참고 자료로 엄격히 제한하여 취급하기로 결정하였다.

## 결정 사항
첫째, API key는 서버 내부에서만 격리 보관하며 Responses API 통신은 서버가 전담한다. 둘째, Todo 영속성은 localStorage를 유지하되 Tool Calling 규격을 엄격히 준수한다. 셋째, 삭제 도구 호출 시 사용자 확인 절차를 필수 구현한다. 넷째, RAG 문서 데이터는 신뢰할 수 없는 외부 입력으로 간주하여 간접 참고 자료로만 모델에 주입한다.

## 후속 작업
개발자는 Express 서버 내 Tool Calling 핸들러 라우트를 구축하고 Responses API 연동 인터페이스를 구현한다. 프로젝트 담당자는 삭제 확인 모달 UI 플로우를 점검하고, RAG 테스트를 위한 샘플 문서 세트 준비를 진행한다.
